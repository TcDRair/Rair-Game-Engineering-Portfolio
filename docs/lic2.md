# LiC2 · AI 역할 조율과 플레이 검증

LiC에서 AI 기반 프로그래밍을 본격적으로 시도한 뒤, LiC2에서는 기획·구현·평가의 역할을 나누고 스프린트마다 범위와 검증 행동을 문서로 연결했습니다. 1인칭 생존·제작 게임의 프로토타입을 진행하며, 구현을 전달받는 과정과 완료를 판단하는 과정을 함께 다뤘습니다.

## 하네스를 구성한 목적

다른 세션에서도 기획 의도, 이번에 만들 범위, 완료 기준이 이어지도록 스펙·계약·평가 기록과 역할별 지침을 묶었습니다. 이 사례에서 하네스는 역할별 세션을 운영하는 규칙과 기록 체계를 가리킵니다. 사람인 제가 각 세션을 수동으로 연결했습니다.

| 역할 | 담당한 일 |
|---|---|
| Planner | 게임·시스템 설계, 스프린트 스펙과 범위 결정 |
| Generator | 스펙을 구현 계약으로 옮기고 코드·씬 작성, 자체 점검 |
| Evaluator | 계약 검토, 코드·씬 확인과 플레이 결과 평가 |
| 저 | 세션 조율, 직접 플레이, 실패 상황 전달과 코드 확인, 일부 임시 수정 |

Generator가 계약 초안을 만들면 Evaluator가 검토한 뒤 구현을 진행했습니다. 계약에는 파일 목록뿐 아니라 “어떤 조작을 하면 무엇이 일어나는가”를 검증 행동으로 적었습니다. 구현 후에는 자체 점검과 별도의 평가를 거치고, 실패한 항목을 수정해 다시 확인했습니다.

## Sprint 6 → 7 · 수정을 반복하다 계약을 다시 정하기

Sprint 6에서는 인벤토리 조작을 연결하며 입력·UI 구성과 아이템 처리 문제가 이어졌습니다. 네 차례 평가 후에도 도달할 수 없는 입력 분기와 아이템 소실 문제가 남아 FAIL로 종료했습니다.

이때 제가 임시로 고쳐서 관찰한 동작과 Generator가 최종 전달한 구현의 동작을 구분해야 했습니다. 사람이 우회한 결과만으로 인도된 구현을 통과시키면, 다음 세션이 실제로 무엇을 받았는지 흐려지기 때문입니다.

Sprint 7에서는 기존 작업을 모두 폐기하지 않고, 보존할 자산과 바꿀 상태 모델을 나눴습니다. 아이템을 임시로 들고 있는 상태를 없애고 이동을 슬롯에 즉시 확정하도록 정리했습니다. UI 입력과 커서 상태도 단일 책임자로 모았습니다.

| 단계 | 계약·평가에서 달라진 점 | 당시 결과 |
|---|---|---|
| Sprint 6 | 여러 인벤토리 조작과 임시 보유 상태를 함께 구현 | 4차 평가에서 FAIL 종료 |
| Sprint 7 계약 | 키보드 조작, 즉시 확정되는 이동, UI 상태 책임을 명시 | 검증할 경로와 범위를 재정의 |
| Sprint 7 평가 | 정적 확인 뒤 실제 플레이, 변경 영향과 빌드 환경을 재확인 | 1·2차 FAIL 이후 3차 PASS |

평가 중 생긴 요구를 모두 결함으로 다루지도 않았습니다. 정렬 시 스택 자동 병합처럼 계약에 없던 동작은 Planner 판단 로그에서 범위 밖으로 남겼습니다. 결함 수정과 새 기능 요구를 구분해 검증 범위가 계속 늘어나는 것을 막았습니다.

## Sprint 8 · 경계 상태를 재현하는 도구까지 전달하기

자원 채집에서는 인벤토리에 들어가지 못한 수량을 월드에 드롭해야 했습니다. 만석 상태만 확인하면 일부만 입고되는 경로는 검증할 수 없었습니다.

초기 인도물에는 부분 여유를 만드는 수단이 빠져 있었습니다. 제가 런타임 값을 임시로 바꿔 확인한 결과는 있었지만, 다른 세션이 같은 상태를 재현할 도구가 필요했습니다. 수정 과정에서 `InventoryFillDebug`의 F7 부분 여유 설정을 추가했습니다.

| 조건 | 재현한 상태 | 관찰한 결과 |
|---|---|---|
| 부분 여유 | 빈 슬롯 0, 목재 98/99, 채집 수율 2 | 입고 1 + 월드 드롭 1 |
| 만석 비교 | 기존 부분 스택 여유가 없는 상태, 수율 2 | 월드 드롭 2 |

F8은 빈 슬롯을 채우는 기능이므로 기존 부분 스택까지 가득 채우지는 않습니다. 완전 만석 비교에서는 시작 상태도 확인해야 합니다.

드롭 위치가 노드나 벽과 겹치는 문제도 함께 드러났습니다. 노드별 오프셋과 씬 배치를 수정한 뒤, 충돌 확인과 실제 회수 경로를 재검증했습니다. 당시 재평가 기록에는 부분 입고의 수량 보존과 배치 결함 해소가 확인되어 Sprint 8 PASS로 남아 있습니다.

## 짧게 남긴 문제 해결

- 초기 비활성 UI 오브젝트는 호출 시점까지 `Awake`가 실행되지 않아 입력 참조가 비어 있었습니다. 파일의 존재뿐 아니라 활성 상태와 호출 순서까지 확인해야 했습니다.
- 디버그 UI 입력을 두 곳에서 받아 한 번의 F1 입력이 두 번의 토글로 이어졌습니다. UI 상태의 책임을 모으는 설계가 실제 구독 경로에도 적용되어야 했습니다.

개별 코드 수정만큼, 실패를 재현하고 다음 역할에 같은 조건으로 전달하는 과정이 중요했습니다. 세션별 역할과 문서가 있어도 실제 플레이와 인도물 기준의 평가가 빠지면 완료 판단은 어긋날 수 있었습니다.

## 기여와 검증 범위

설계·계약·코드·평가에 AI가 참여했습니다. 제 기여는 역할과 작업 흐름을 운영하고, 직접 플레이한 결과와 코드를 바탕으로 다음 수정을 연결한 데 있습니다. 모든 코드를 직접 작성한 프로젝트로 소개하지 않습니다.

이 문서의 PASS·FAIL과 수치는 당시 계약·평가 기록을 요약한 것입니다. 이번 포트폴리오 정리에서 새로 실행한 테스트 결과는 아닙니다. 사례와 구현은 LiC2의 dev 브랜치를 기준으로 합니다.
