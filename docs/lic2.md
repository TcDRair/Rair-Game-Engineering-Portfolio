# LiC2 · 에이전트 역할 조율과 스프린트 운영

1인칭 생존·제작 프로토타입을 개발하며 Planner·Generator·Evaluator 세션을 나누고, 스펙·계약·구현·평가 기록을 연결했습니다. 제 역할은 세션 사이의 작업을 조율하고, 직접 플레이와 코드 확인으로 다음 판단에 필요한 정보를 전달하는 것이었습니다.

## 하네스 도입 배경

LiC에서 AI 기반 프로그래밍을 본격적으로 시도한 뒤, 후속 LiC2에서는 여러 시스템을 스프린트 단위로 이어 갔습니다. 서로 다른 세션에서도 기획 의도, 구현 범위, 완료 기준을 함께 유지할 운영 체계가 필요했습니다.

역할별 지침과 문서, 계약 검토, 평가와 재검증 절차를 하네스로 구성했습니다. 스프린트마다 맡길 범위와 범위 밖 항목을 정하고, 확인할 행동과 결과를 기록해 다음 세션의 입력으로 넘겼습니다.

## 역할과 전달물

| 역할 | 받는 것 | 남기는 것 |
|---|---|---|
| Planner | 게임·시스템 설계, 이전 평가와 미해결 사항 | 스프린트 스펙, 범위와 설계 판단 |
| Generator | 스펙과 계약 검토 피드백 | 계약 초안, 구현물, 자체 점검과 알려진 한계 |
| Evaluator | 스펙·계약, 인도된 구현물과 플레이 관찰 | 계약 보완 요청, PASS·FAIL, 수정·재검증 항목 |
| 저 | 각 역할의 결과와 실제 실행 상태 | 다음 세션에 전달할 맥락, 직접 플레이한 실패 상황, 코드 확인과 일부 임시 수정 |

Generator가 구현 계약을 작성하면 Evaluator가 먼저 검토했습니다. 승인된 계약을 기준으로 구현과 자체 점검을 진행하고, 별도 평가에서 코드·씬 구성과 실제 플레이를 확인했습니다. 제가 각 단계의 세션을 수동으로 연결했습니다.

평가 결과에 따라 다음 경로를 구분했습니다.

- 구현 결함은 Generator 수정과 Evaluator 재검증으로 연결했습니다.
- 계약에 없는 요구나 설계의 모호함은 Planner 판단으로 돌렸습니다.
- 현재 계약으로 해결을 이어 가기 어려운 경우에는 실패로 종료하고 다음 스프린트의 입력으로 정리했습니다.

## 스프린트 1~8

| 스프린트 | 작업 범위 | 조율·검증에서 다룬 점 | 당시 최종 평가 |
|---|---|---|---|
| 1 | 프로젝트·패키지·조명·버전 관리 기반 | URP의 실제 설정 구조와 문서의 의도를 대조 | PASS · 4/26 |
| 2 | 1인칭 조작·상호작용·HUD | 입력 방식과 한글 폰트 누락을 인도물에 반영한 뒤 재검증 | PASS · 4/27 |
| 3 | 플레이어 니즈·HUD 해금·상태 효과 | 로직, 에셋 연결, 카메라 설정과 실제 화면을 함께 확인 | PASS · 5/7 |
| 4 | 작업실 그레이박스·구획 감지 | 자동 판정과 디버그 오버라이드, 기존 상태 시스템의 회귀 확인 | PASS · 5/12 |
| 5 | 디버그 HUD 사용성·경계값 검증 | 검증 도구가 시뮬레이션을 덮어쓰는 문제를 수정·재평가 | PASS · 5/13 |
| 6 | 인벤토리·아이템 픽업과 조작 | 네 차례 평가 후 잔여 결함과 계약의 공백을 다음 단계로 이관 | FAIL · 5/19 |
| 7 | UI 상태 책임·인벤토리 조작 재설계 | 보존할 자산과 바꿀 상태 모델을 나누고 범위 판단·재검증 | PASS · 6/10 |
| 8 | 홀드 채집·재생·수율 처리 | 경계 상태의 재현 수단까지 인도물로 포함해 재검증 | PASS · 6/24 |

날짜는 2026년 평가 기록 기준입니다. 같은 스프린트 안의 초기 FAIL과 수정 과정도 기록에 보존했습니다.

## 조율 과정에서 되돌아본 세 가지 결정

### 수정의 반복을 멈추고 새 계약으로 넘기기

Sprint 6에서는 입력 분기와 아이템 소실 문제가 반복됐고, 임시 보유 상태의 종결 조건도 계약에서 빠져 있었습니다. 제가 임시로 수정한 코드 위에서 관찰한 결과와 Generator가 전달한 구현의 상태도 구분해야 했습니다.

네 번째 평가에서 FAIL로 종료하고, 남길 자산과 재설계할 문제를 Sprint 7의 입력으로 넘겼습니다. 후속 계약에서는 임시 보유 상태와 UI 상태 책임을 다시 정했습니다.

### 결함 수정과 추가 요구를 구분하기

Sprint 7의 정렬 과정에서 스택 자동 병합 여부가 쟁점이 됐습니다. Planner 판단 로그에서 기존 정렬 기준과 새 요구를 구분하고, 현재 계약의 검증 범위를 유지했습니다. 구현 결함의 수정 흐름과 범위 결정이 섞이지 않도록 연결한 사례입니다.

### 다른 세션이 재현할 수 있는 상태를 전달하기

Sprint 8에서는 부분 여유가 있는 인벤토리를 재현하는 도구가 인도물에서 빠져 있었습니다. 임시 수치 변경으로 확인한 결과를 넘기는 데서 그치지 않고, 같은 조건을 만들 수 있는 디버그 경로를 추가하도록 연결했습니다. 이후 일부 입고·초과 드롭과 배치 충돌을 재검증했습니다.

## 기여와 기록

설계·문서·코드·평가에 AI가 참여했습니다. 저는 역할별 세션을 운영하고, 직접 플레이한 실패와 코드 확인 결과를 전달하며, 다음 수정이나 설계 판단으로 연결했습니다.

위 PASS·FAIL은 당시 계약과 평가 기록을 요약한 것입니다. 이번 문서 정리에서 새로 실행한 테스트 결과는 아닙니다. 구현 사례는 LiC2의 dev 브랜치를 기준으로 합니다.
