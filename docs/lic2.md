# LiC2 · 에이전트 역할 조율과 스프린트 운영

1인칭 생존·제작 프로토타입을 개발하며 Planner·Generator·Evaluator 세션을 나눴습니다. 저는 세션을 수동으로 조율하고, 직접 플레이와 코드 확인 결과를 다음 작업으로 연결했습니다.

## 하네스 도입 배경

LiC에서 AI 기반 프로그래밍을 시도한 뒤, LiC2에서는 여러 시스템을 스프린트 단위로 이어 갔습니다. 다른 세션에서도 기획 의도·구현 범위·완료 기준을 유지하도록 역할 지침과 스펙·계약·평가 기록, 재검증 절차를 하네스로 구성했습니다.

## 역할과 전달물

| 역할 | 받는 것 | 남기는 것 |
|---|---|---|
| Planner | 게임·시스템 설계, 이전 평가와 미해결 사항 | 스프린트 스펙, 범위와 설계 판단 |
| Generator | 스펙과 계약 검토 피드백 | 계약 초안, 구현물, 자체 점검과 알려진 한계 |
| Evaluator | 스펙·계약, 전달된 구현물과 플레이 관찰 | 계약 보완 요청, PASS·FAIL, 수정·재검증 항목 |
| 저 | 각 역할의 결과와 실제 실행 상태 | 다음 세션에 전달할 맥락, 직접 플레이한 실패 상황, 코드 확인과 일부 임시 수정 |

Generator의 구현 계약을 Evaluator가 검토한 뒤 구현과 자체 점검을 진행했습니다. 별도 평가에서 코드·씬 구성과 실제 플레이를 확인하고, 결과에 따라 다음 작업을 정했습니다.

- 구현 결함: Generator 수정 후 Evaluator 재검증
- 범위·설계 문제: Planner 판단으로 스펙·계약 정리
- 구조적 결함의 반복: 실패 종료와 잔여 문제 기록 후 다음 계약으로 이관

## 조율 과정의 주요 결정

### 수정의 반복을 멈추고 새 계약으로 넘기기

Sprint 6에서는 입력 분기와 아이템 소실 문제가 반복됐고, 임시 보유 상태의 종결 조건도 계약에서 빠져 있었습니다. 제가 임시로 수정한 코드 위에서 관찰한 결과와 Generator가 전달한 구현의 상태도 구분해야 했습니다.

네 번째 평가에서 FAIL로 종료하고, 남길 자산과 재설계할 문제를 Sprint 7의 입력으로 넘겼습니다. 후속 계약에서는 임시 보유 상태와 UI 상태 책임을 다시 정했습니다.

### 결함 수정과 추가 요구를 구분하기

Sprint 7의 정렬 과정에서 스택 자동 병합 여부가 쟁점이 됐습니다. Planner 판단 로그에서 기존 정렬 기준과 새 요구를 구분하고, 현재 계약의 검증 범위를 유지했습니다.

### 다른 세션이 재현할 수 있는 상태를 전달하기

Sprint 8에서는 부분 여유가 있는 인벤토리를 재현하는 도구가 전달물에서 빠져 있었습니다. 임시 수치 변경으로 확인한 결과를 넘기는 데서 그치지 않고, 같은 조건을 만들 수 있는 디버그 경로를 추가하도록 연결했습니다. 이후 일부 입고·초과 드롭과 배치 충돌을 재검증했습니다.

설계·문서·코드·평가에 AI가 참여했습니다. 당시 LiC2 dev 브랜치와 스프린트 기록을 기준으로 정리했으며, 원본 저장소는 현재 비공개입니다.
